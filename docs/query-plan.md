# 可组合查询计划（未实现）

> 状态：2026-10-05 已完成并验收 P0 测量：Codex 罕见单词首批结果中位数 154.12ms，超过 100ms。数据、前置崩溃修复与限制见 [architecture.md](architecture.md#项目搜索性能基线)。性能方案已定（D20）：先做 P0.5 扫描提速，不做三元组索引；之后继续 P1–P4。**以下查询和界面能力均未实现**，不得写入 README 或[产品说明](product.md)作为现有功能。
> 原型：[query-prototype.html](query-prototype.html)（浏览器打开，可切三主题）。
> 完成后把仍有效的行为归入 `product.md`，删除本文件和原型。

## 为什么做

现在的项目搜索（`⇧⌘F`）一次只能找一个模式串，再加大小写、全词、正则和包含/排除路径。读陌生项目时常见三种困难，它都帮不上：

1. **结果太多太杂**：想去掉测试、注释或某些目录里的命中。
2. **找不到“同时出现”**：比如 `lock` 和 `await` 在同一个函数里出现的地方。
3. **看不出命中属于谁**：结果只有“文件:行号”，要逐个点开才知道在哪个函数里。

另外，搜索面板浮在窗口上，失去焦点就隐藏。组合查询的结果通常是一份要逐条看完的清单，不适合这种用法。

- **收藏查询**、在概览竖条上显示项目搜索命中。
- 任何 AI 相关能力（自然语言转查询等）。

## 共同约束

1. **简单搜索不变慢、不多一步**。只输入一个词时，结果与今天相同，入口和按键次数不增加。
2. **诚实**。组合条件会排除结果；结果必须说清搜了什么、跳过了什么、哪里被截断（S4）。“同一函数”“在注释里”都来自语法分析，不代表语义判断。
3. **与阅读区一致**。“什么是注释、什么是字符串”与阅读区语法高亮的判断一致；“所在函数”与 Context 的“所在函数”模式一致。
4. **三主题统一**。Light、Dark、SI Classic 各有一套取值；条件颜色不与多色高亮、同名高亮、diff 色混淆。
5. **键位进入集中表**。新命令注册到 `KeyBindings` 默认表，通过冲突校验，可在设置里改。
6. **双语**。新文案同时提供 `en` 与 `zh-Hans`。

## S1 查询语法与条件控件

**语法**（沿用 GitHub 代码搜索的写法，再加 Cairn 的结构条件）

| 写法 | 含义 |
| --- | --- |
| `lock await` | 空格分隔的各项都要满足（并且） |
| `lock OR mutex` | 任一满足即可（或者）；`OR` 必须大写 |
| `-test` | 排除 |
| `"fn spawn("` | 精确短语，可以包含空格和符号；`\"` 表示引号本身 |
| `/sp[a-z]+n/` | 这一项按正则匹配；`\/` 表示斜杠本身 |
| `path:src/runtime/`、`-path:tests/` | 只看 / 不看这些路径，glob 语法同现有路径过滤；多个 `path:` 取并集 |
| `in:code`、`in:comment`、`in:string`、`-in:comment` | 只在 / 不在这些区域里匹配；可写多个 |
| `near:5` | 各条件的命中相距不超过 5 行 |
| `same:fn` | 各条件的命中在同一个函数里 |

- **S1.1** `OR` 比空格结合得紧：`lock OR mutex await` 表示“（lock 或 mutex）并且 await”。没有括号，所以一个查询总是“若干条件同时满足”，每个条件可以有几个备选。
- **S1.2** 排除项不能用 `OR` 连接：`-a OR b` 报错并提示改写为 `-a -b`。
- **S1.3** 只有已知的限定词（`path`、`in`、`near`、`same`）后面跟冒号才算限定词，所以 `std::sync`、`http://` 仍是普通文字。
- **S1.4** `-` 只在后面紧跟字母、数字、`_`、引号、斜杠或限定词时表示排除；`->`、`-=` 按普通文字搜索。
- **S1.5** 大小写、全词、正则三个开关保留为按钮，不写进语法。大小写作用于所有项；全词和正则只作用于没有引号也没有斜杠的普通词。打开正则开关后，普通词按正则匹配，含空格的正则需写成 `/a b/`。
- **S1.6** 粘贴到空输入框的文本如果含空格，自动加上引号，作为一个精确短语。在阅读区选中文字后执行项目搜索也一样。这样粘贴一段代码不会被拆成几个“并且”。手动输入的多个普通词按“并且”理解：今天输入 `fn spawn` 按整句搜索，以后是两个条件同时满足（D16）。
- **S1.7** 语法有错时，停顿约 0.6 秒后在输入框下方显示一行错误说明，并标出出错位置（打到一半的 `same:f` 不会立即报错）；不执行搜索，保留上一次的结果和条件标签。

**条件控件**

- **S1.8** 输入框下方是一行条件标签，每个标签对应语法里的一项：包含（含备选）、排除、路径、区域、范围。点标签可以编辑或删除；行尾“+ 添加条件”菜单列出所有条件种类。
- **S1.9** 双向同步：在输入框里打字，标签实时更新；改标签会改写输入框里的文字，光标位置尽量保持。两边表达的是同一个查询，不另存一份状态。
- **S1.10** 只有一个普通词时不显示标签行，界面和今天一样。
- **S1.11** 每个“包含”条件按顺序取一种条件色，四色循环；条件色只用于小色块和命中下划线，不用底色，与多色高亮、同名高亮的底色区分（D19）：

## S2 组合语义

**命中单位**

- **S2.1** 默认按**文件**：文件里每个“包含”条件都至少命中一次，并且没有任何“排除”条件的命中，这个文件的命中才保留。
- **S2.2** `same:fn`：按**函数**判断，规则同上。函数取最内层的函数或方法；嵌套在函数里的闭包、箭头函数算外层函数的一部分；不在任何函数里的顶层闭包或箭头函数自成一个函数。不在任何函数里的命中不出现在结果中。
- **S2.3** `near:N`：按**行距**判断。某处命中保留的条件是：前后 N 行内，其他每个“包含”条件都至少命中一次，并且没有“排除”条件的命中。
- **S2.4** `near:N` 和 `same:fn` 可以同时写，两个条件都要满足。
- **S2.5** 只有一个“包含”条件时，`near:` 和 `same:fn` 只影响排除的范围。例如 `unwrap -test same:fn` 表示“不在含 test 的函数里的 unwrap”。

**区域与路径**

- **S2.6** `in:` 对所有条件生效，包括排除条件。例如 `lock -test -in:comment` 中，注释里出现的 `test` 不会导致排除。
- **S2.7** 命中的起点落在注释或字符串范围里，就算作在注释或字符串里。区域划分与阅读区高亮一致；Python docstring 等边界情况也跟随阅读区。
- **S2.8** `path:` 在读文件之前过滤，与现有的包含/排除路径相同；不再单独保留旧的路径输入行，旧输入行的内容迁移成 `path:` 条件。

**结果行**

- **S2.9** 结果列出所有“包含”条件在保留单位里的命中，每行标出命中的是哪个条件（与标签同色的小色块）。排除条件只用于过滤，不产生结果行。
- **S2.10** 同一行命中多个条件时只列一行，带多个色块。

## S3 结果停靠区

- **S3.1** 项目搜索的结果不再放在浮动面板里，而是停靠在主窗口底部，与 Context 共用底部区域，用“Context / 搜索结果”两个标签切换（D17）。
- **S3.2** `⇧⌘F` 打开停靠区并把焦点放进输入框；在阅读区选中文字时，选中的内容会带入输入框（见 S1.6）。Esc 把焦点还给阅读区，但停靠区保持打开；用关闭按钮或再次执行“显示/隐藏搜索结果”才收起。
- **S3.3** 结果按文件分组，文件下面直接列出命中的行。每行前面标出所在符号：
  - 在函数或方法里，显示函数名；方法带上所属类型，例如 `Mutex::lock`。
  - 不在函数里，就显示所在的类型、impl 或模块。
  - 都不在，就留空。
  - 连续几行属于同一个符号时，只在第一行显示，后面用一条细竖线表示延续。

  符号显示在行号左侧的固定宽度列（约 150pt，超出截断，悬停显示全名）（D18）。
- **S3.4** 单击结果行：在阅读区的预览标签打开这一处，选中命中并闪烁，焦点仍留在结果列表，所以可以用方向键逐条浏览。双击或回车：打开并把焦点交给阅读区。
- **S3.5** “下一处搜索结果 / 上一处搜索结果”（拟定 `⌥⌘G` / `⇧⌥⌘G`，需通过冲突校验）在任何焦点下都可用，按结果列表的顺序逐条打开，列表同步选中这一条。文件内查找的 `⌘G` 不受影响。
- **S3.6** 快照变化（刷新工作区、切换 commit）后，用同一个查询自动重搜。重搜期间旧结果变灰并标明“已过期”，新结果到达后替换，不在旧结果上跳到错误位置。
- **S3.7** 查询历史：
  - 每个项目保存最近 20 条，随阅读会话保存，“清除阅读会话”时一并清除。
  - 输入框在行首按 ↑，或者点击历史按钮，可以调出历史。
  - 历史条目同时保存三个开关的状态。
- **S3.8** 停靠区是否打开、尺寸、最后一次查询都随布局和会话恢复。项目重新打开、索引就绪后，自动执行最后一次查询。
- **S3.9** 三个开关（大小写、全词、正则）沿用现在的规则，按窗口记住。

## S4 覆盖范围与截断

- **S4.1** 结果底部写明：
  - 搜索了哪些语言的多少个源文件；
  - 按 `path:` 排除了多少个；
  - 按项目规则排除了多少个路径；
  - 没有搜索多少个非源码文件；
  - 正则跳过了多少个大文件。
  
  数量为零的项不显示。
- **S4.2** 组合查询会对每个条件分别搜索，每个条件各自受现有上限约束：每个文件 200 处、总共 5,000 处、5 秒。只要有一个条件被截断，结果就标明“可能不完整”，并指出是哪一个条件；被截断的文件在列表里单独标记。
- **S4.3** 结果列表最多显示 2,000 行（与现在相同），超出时说明。

## S5 查询提示

- **S5.1** 触发条件（只在输入框有焦点时）：
  - 输入框为空，停顿约 2 秒；
  - 有了查询，停顿约 2 秒后仍然没有结果；
  - 结果被截断，或者超过了显示上限。

  结果正常时不弹。
- **S5.2** 提示的内容根据当前查询生成：
  - 输入框为空时，给出 2–3 条典型写法；
  - 没有结果时，提示放宽条件，例如去掉 `same:fn`、改成 `near:20`、去掉 `in:`；
  - 结果太多时，提示收紧条件，例如加 `in:code`、`same:fn`，或者排除命中最多的测试目录。
- **S5.3** 形式（节奏按原型，D19）：
  - 能直接接在当前输入后面的那一条，用灰色文字在输入框里续写出来，每字约 28ms 逐字出现，后面带一个 `Tab` 键帽提示，按 Tab 接受；
  - 输入框下方浮出一个气泡（约 0.18 秒淡入并上移 6pt），列出 2–3 条，每条附一句说明。点一条就应用；Esc 或继续输入就收起。
- **S5.4** 系统开启“减弱动态效果”时，提示直接显示，不播放动画。
- **S5.5** 频率：
  - 用户成功用过某个语法以后，这个语法不再出现在提示里（应用级记录）；
  - 同一次搜索里被关掉的提示，不再弹出；
  - 设置里可以关闭“显示查询提示”。
- **S5.6** 输入框旁边的“?”按钮随时打开完整的语法速查，不受 S5.5 限制。

## S6 索引：注释与字符串范围

- **S6.1** 建索引时，在现有的 tree-sitter 解析里顺带记录注释和字符串的字节范围，存进 `ContentIndex`，并随 SQLite 缓存保存。搜索时直接查表，不在搜索时重新解析。
- **S6.2** 记录要完整，不受抽取器为了找符号而跳过的子树影响：
  - Rust 宏调用里的字符串和注释要记录，比如 `println!("…")`；
  - TypeScript 在声明、导入、导出分支里提前返回而漏掉的部分要补上。
- **S6.3** 这项改动要提高抽取器版本，缓存会失效：升级后第一次打开项目时，所有源文件重新解析一遍。
- **S6.4** 不写专用的轻量扫描器。只有 S8 实测证明解析是瓶颈时，才重新考虑。

## S7 命令行

- **S7.1** `codeinsight search '<查询>'` 接受与应用相同的语法，并增加 `--whole-word`。查询解析和求值放在引擎里，应用和命令行共用一套实现。
- **S7.2** 文本和 JSON 输出：每处命中带上所属符号和命中的条件，末尾附覆盖范围（S4.1）和截断情况。

目标（起点，实测后校准）：

- **S8.1** 索引就绪后，简单搜索在 100ms 内显示第一批结果。

- **S8.3** 加入注释和字符串范围后，首次建索引的耗时增加不超过 10%，缓存体积增加不超过 15%。

测量：

- 在实施的第一步，先测出现状：tokio 与 Codex 的首次建索引耗时、缓存命中后的建索引耗时，以及索引就绪后单次搜索的延迟。
- 搜索延迟不包含建索引。
- 结果写进 [architecture.md](architecture.md)，注明日期、版本、机器和局限。

**三元组索引**不在本计划内（D20）。P0.5 之后若 S8.1 或 S8.2 仍达不到，再带数据讨论。

| D16 | 多个普通词的含义 | 按“并且”理解，接受与今天不同；粘贴和选中带入的含空格文本自动加引号 |

### P0 测量（已完成，2026-10-05 验收）

`search --repeat N` 与隔离冷/热索引测量已完成，命令归入 [development.md](development.md#性能复现)，结果归入 [architecture.md](architecture.md#项目搜索性能基线)。Codex 罕见词首批 154ms，未达到 S8.1。

验收时对同一二进制采样（`sample`，罕见词连续重复搜索，按采样比例折算到一次 154ms）：

| 部分 | 约占 | 原因 |
| --- | --- | --- |
| 搜索前准备 | 40ms | `SnapshotSearchService.activeFiles()` 对每个文件调用 `LanguageMode.classify(path:language:)`，其中 `URL(fileURLWithPath:)` 每次都触发一次 `getcwd` 系统调用 |
| 逐字节比较 | 90ms | `literalRanges` 单线程，每移动一个字节都构造 `ByteRange`、判断大小写分支 |
| 行号表 | 18ms | 没有命中的文件也构建 `LineTable` |

另外，引擎要攒够 16 个文件或 200 条命中才发送中间批次，罕见词的首批就等于扫描结束。独立实验（同一批 Codex 文件，大小写不敏感，`swiftc -O`）：紧凑的单线程循环约 43ms，按文件并行（`concurrentPerform`）约 6ms。实验程序不在仓库中，只作为方向依据。

### P0.5 扫描提速（S8.1，D20）

目标：在不改变任何搜索结果的前提下，让 Codex 罕见词的首批结果低于 100ms（预期 20ms 以内），其他查询不变慢。不新增索引或缓存，内存不明显增加。

1. **语言分类**：`LanguageMode.classify(path:language:)` 改为直接按路径字符串判断扩展名，不再构造 `URL`。判断规则保持不变，包括 `.pyi`、`.d.ts`、`.mts`、`.cts` 不算源码（见 product.md 限制表）。如果其他调用方依赖 `URL` 的规范化行为，就改为在 `EngineSession` 上缓存“当前语言的文件列表”，按快照失效。两种做法任选，以不改变分类结果为准。
2. **行号表**：只为有命中的文件构建 `LineTable`。
3. **字面量比较**：重写 `literalRanges` 的循环。
   - 区分大小写和不区分大小写各写一条循环，先过滤首字节再逐字节比较；只在确认命中时构造 `ByteRange`。
   - 每 4 KiB 检查一次取消和超时，保持不变。
   - 语义完全不变：命中后从命中末尾继续找，不重叠；全词检查失败时从下一个字节继续，所以仍能找到重叠位置上的命中；每个文件最多 200 条命中，超出时与现在一样多收一条，作为截断标记。
4. **并行**：`SnapshotSearchService.search` 把内容列表分给 `activeProcessorCount` 个工作任务，每个任务处理一段连续的文件。
   - 结果按原来的文件顺序汇总，所以总数 5,000 条的截断落在哪些命中上，与串行实现一致。
   - 正则路径也一起并行；`NSRegularExpression` 实例的线程安全按 Apple 文档确认，必要时每个工作任务各用一个实例。
   - 取消搜索时，所有工作任务都要停下，之后不再发送任何批次；5 秒超时与截断的语义不变。
5. **首批发送**：一旦有命中，立刻发送第一批；之后在现有阈值（16 个文件或 200 条命中）和距上次发送 50ms 中，先到者触发下一批。

**P0.5 验证**
- **属性测试（`literalRanges`）**：把现有实现原样复制到测试目标里作为参照，用固定种子生成输入，新旧实现结果必须一致。输入覆盖：ASCII 大小写混合、多字节 UTF-8、可重叠的模式（`aa` 搜 `aaaa`）、全词、超过上限的命中数、模式比内容长。
- **属性测试（语言分类）**：新旧分类在生成路径上结果一致。路径覆盖：大写扩展名、多个点、`.d.ts`/`.mts`、无扩展名、带 `..` 的相对路径。
- **集成测试（搜索服务）**：在一个 fixture 项目上，并行结果与“工作任务数为 1”的结果逐条相同，包括截断时的结果。为此需要把工作任务数和两个上限设为内部可注入的参数。
- **集成测试（取消）**：取消后流在有限时间内结束，之后没有新批次。
- **性能**：用 P0 的同一组命令和语料复测 tokio 和 Codex 的六个查询，更新 [architecture.md](architecture.md#项目搜索性能基线) 的表格，保留提速前的数字作对照。Codex 罕见词首批要低于 100ms；其他查询的首批和结束时间都不能比 P0 慢。

### P1 引擎：查询、区域与命令行（S1 语法、S2、S4、S6、S7）

1. **区域数据（S6）**
   - 给 `ContentIndex` 加一个按起点排序的注释/字符串范围数组。
   - 三个抽取器在现有解析结束后，对整棵语法树做一次只认节点种类的遍历。这次遍历不跳过宏、导入、导出等子树。
   - 节点种类表从阅读区高亮现有的分类里抽出来，放到两边都能引用的位置（`TreeSitterKit` 或各语言抽取器的 Info），阅读区改为引用同一张表。
   - 提高三个 `extractorVersion`。如果编码字段需要变，同时提高 `ContentIndexDraftCodec.formatVersion`，并扩展 `isValid`、`remap` 和 CanonicalDump。
2. **查询类型**
   - 在 `CodeInsightEngine` 新建查询的解析与序列化：文本 ⇄ 结构，错误带出错范围。
   - 结构包括：若干“包含”条件（每个条件有若干备选项）、排除项、路径 glob、区域集合、`near`、`same:fn`。
   - 每一项的匹配复用 `ContentSearchQuery` 的字面量、正则和全词逻辑。`searchReferences` 不变。
3. **求值**
   - `SnapshotSearchService` 增加按查询结构搜索的入口：先按路径过滤；再对每个文件逐项找命中，并按区域过滤（二分查找）；最后按文件、函数或行距判断，规则见 S2。
   - 函数单位取 `ContentIndex.scopes` 中最内层的函数或方法作用域；闭包归入外层函数，顶层闭包自成一个单位。
   - 每个条件分别计入现有上限，被截断的条件记入结果。
4. **结果**
   - `SearchMatch` 增加命中的条件集合，以及所在符号的显示名：方法取 `类型::名称`，Python 和 TS 用 `.` 连接，与块尾注解的取名规则一致。显示名只为送出的批次计算。
   - `SearchBatch` 增加覆盖范围所需的计数：非源码文件数、正则跳过的大文件数、被截断的条件。
5. **命令行（S7）**
   - `search` 使用同一套解析，增加 `--whole-word`。
   - 文本和 JSON 输出带上条件、符号和覆盖范围。

**P1 验证**
- **属性测试**：
  - 解析与序列化往返稳定（`parse(serialize(q)) == q`）；
  - 用独立的朴素求值器作参照：在生成的小文件和查询上，结果与 `SnapshotSearchService` 一致，覆盖 `near`、`same:fn`、排除和区域；
  - 固定随机种子。
- **一致性检查**：在 Rust、Python、TS 的 fixture 上，区域分类与阅读区高亮的注释和字符串范围一致，覆盖 `println!("…")`、原始字符串、docstring、模板字符串。
- **集成测试**：
  - 提高版本后，旧缓存被重新抽取，不会解码失败；
  - 命令行 JSON 的结构。
- **用 P0 的方法复测 Codex**：首次建索引的耗时和缓存体积不超过 S8.3 的上限。
